  what to type next: fix the character or literal the message names; `cig language` shows the forms

     probe: source-line (the source line under the caret)
     remedy: fix it at the caret

  arises in: parse  ·  tags: beginner-likely

======== E101 ========
E101 unterminated string  (lex, lex family, since 1.0.0)

  kind of no: not one of the four  (a mistake in the text, in the arithmetic, or in CigScript; syntax, type or logic error; an internal error)

  A string literal has no closing quote on its line.

  what to type next: close the string on the same line, or write \n for a newline inside it

  known causes, ranked; doctor checks them in this order
  1. the closing quote is missing, or sits on the next line
     probe: string-literal-scan (the line the string opened on, looking for where the quote should close)
     remedy: close the string on the line it opened; use \n for a line break inside it
  2. an escaped quote \" swallowed the closing quote
     probe: source-line (the source line under the caret)
     remedy: count the backslashes before the last quote; a raw 'single-quoted' string has no escapes

  arises in: parse  ·  tags: beginner-likely

======== E102 ========
E102 unknown escape  (lex, lex family, since 1.0.0)

  kind of no: not one of the four  (a mistake in the text, in the arithmetic, or in CigScript; syntax, type or logic error; an internal error)

  A backslash sequence in a double-quoted string is not one CigScript knows.

  what to type next: use \n \t \r \0 \\ \" \$ \u{hex}; for a regex or a Windows path use a raw 'single-quoted' string

     remedy: write it as a raw 'single-quoted' string, which has no escapes at all
  2. a typo in an escape

  arises in: parse  ·  tags: beginner-likely

======== E720 ========
E720 a rekey cannot be done  (burn, kernel family, since 1.19.0)

  kind of no: one of the four; the message says which  (read the operating-system reason in the message; ENOENT, EACCES, ENOSPC and friends, each mapped in the causes below)

  cig tin rekey refuses because what it needs is not here, is already in use, or would launder tampering. The current key must be available (otherwise there is nothing to re-seal from), and the keeper must be one a rekey can write to (keyring or key file). An interrupted earlier rekey that left behind a seal.key.old file that is not a key is also this code. The rekey takes an exclusive lock on the tin: a second cig tin rekey while one is held is refused outright, named. Every format-3 journal and the ledger are verified under the current key before anything is re-signed; a chain that does not fit refuses the rekey, naming the run, and leaves the tampered bytes on disk so they can be looked at. The keeper swap at the end is read back: a keeper that would not carry the new key refuses, leaves both stashes on disk (every sealed object stays readable under the fallback), and a later cig tin rekey finishes the job. Nothing on disk is changed before the walk begins.

  what to type next: put the current key back (cig tin key import), or store it where a rekey can swap it (cig config seal_key keyring); after a bad seal.key.old, move it aside and run cig tin rekey again; wait for the holder of the rekey lock; fix the tampered journal cig names before trying again

  known causes, ranked; doctor checks them in this order
  1. the current tin key is not available (no keyring entry, no key file, nothing on --seal-key-fd)
     probe: path-exists (stat of the path named in the message)
     remedy: cig tin key import the key you exported earlier, or put the keyring entry back (cigscript/tin-seal)
  2. the key came in on --seal-key-fd for this run only, so a rekey has no keeper to write to
     probe: env-var (an environment variable that changes the limit involved)
     remedy: cig config seal_key keyring (or seal_key file) first, so the new key has somewhere to live
  3. an earlier rekey crashed and left a seal.key.old that no longer reads as a key
     probe: path-exists (stat of the path named in the message)
     remedy: move the file aside (it is in the keys directory); the rekey picks up from a clean state on the next run
  4. another cig tin rekey is in progress on this tin
     probe: path-exists (stat of the path named in the message)
     remedy: wait for the other one to finish; if it crashed, run cig tin rekey again and it picks up the walk
  5. a run's journal, or the ledger, does not verify under the current key
     probe: path-exists (stat of the path named in the message)
     remedy: the run is named in the message; investigate the edit and either put the chain back (a backup) or move the run aside before running cig tin rekey again
  6. the keeper would not carry the new key (keyring write failed the read-back, or the key file could not be written)
     probe: none; a suggestion, not a finding
     remedy: both stashes stay on disk and every sealed object is still readable; fix the keeper (unlock the keyring, free space on the keys filesystem) and run cig tin rekey again to finish

  arises in: run  ·  related: E703, E707, E708, E709  ·  tags: kernel

======== E721 ========
E721 the tin's key folder is not private  (burn, kernel family, since 1.19.0)

  kind of no: these are MY ciggies  (the door: it knows you and said no; 403 Forbidden; permission denied; a lock; a refusal by policy)

  The keys folder beside the state root holds the seal key, the ledger and the rekey lock; for the tin's history and its sealed objects to mean anything, that folder and the files in it must be yours and closed to other users. cig refuses when they are not: a folder another user owns or others can write to; a seal.key, ledger.jsonl or rekey.lock another user owns, or one that is a symlink or not a file; a seal.key others could read or that has a second name (a hard link), checked when the key is read from it. Nothing is signed, sealed or read under it. A ledger or lock of yours that is only too open holds no secret, so cig makes it 0600 and goes on. With CIGSCRIPT_HOME under a shared parent (such as /tmp, /var/tmp or /dev/shm) the folder has a per-user name (.cigscript-keys-<uid>), so two users under the same parent never share one; a folder of yours under the old shared name, still private, stays in use. Owners are named by uid (getent passwd <uid> names them). The folder is made 0700 from the start; CIG_KEYS_DIR and CIG_SEAL_KEY_FILE point somewhere else but do not weaken the checks.

  what to type next: a folder or file that is yours, made under sudo: chown it back to yourself. One that is not yours: move it aside (it is not your key), or set CIG_KEYS_DIR to a folder only you can write. A seal.key others could read: chmod 600 it, then cig tin rekey if anyone else could have read it; never move your own key aside, a new key opens nothing the old one sealed

  known causes, ranked; doctor checks them in this order
  1. another user owns the keys folder (someone made your per-user name under a shared parent first), or it is yours but was made under sudo
     probe: path-exists (stat of the path named in the message)
     remedy: made under sudo: chown it back to yourself; not yours: you cannot use it, so set CIG_KEYS_DIR to a folder only you can write, or keep CIGSCRIPT_HOME out of a shared folder
  2. the keys folder is group- or world-writable, so someone else could plant seal.key or delete the ledger
     probe: path-exists (stat of the path named in the message)
     remedy: chmod 700 the folder, or set CIG_KEYS_DIR to a folder only you can write
  3. seal.key is readable by group or world, so someone else may have read the key, or it has a second name (a hard link) it can be read through
     probe: path-exists (stat of the path named in the message)
     remedy: chmod 600 it (a hard link: copy the key beside itself and move the copy over it), then cig tin rekey if anyone else could have read it; keep the file, a new key opens nothing the old one sealed
  4. seal.key, ledger.jsonl or rekey.lock is owned by another user, or is a symlink or not a file, so a read may be redirected or the file planted
     probe: path-exists (stat of the path named in the message)
     remedy: yours, made under sudo: chown it back; a link: put the real file back in place; not yours: move it aside, or set CIG_KEYS_DIR / CIG_SEAL_KEY_FILE to a path only you can write

  arises in: run, any  ·  related: E707, E720  ·  tags: kernel

This one cannot open its file (installed execute-only, such as mode 0711, and run by someone without read permission), so it cannot tell whether it is a program, and it refuses rather than act as a general cig. A binary named cig or cig-runtime is cig, and runs as cig either way.

  what to type next: make it readable by whoever runs it (chmod 755), as cigcompile writes it

  known causes, ranked; doctor checks them in this order
  1. the program was installed execute-only, to ship a tool without handing out its contents; a program's script is in its file, so it must read it
     probe: path-permissions (mode bits and owner of the path, or of its nearest existing ancestor)
     remedy: chmod 755 the program

======== E1052 ========
E1052 not one of the program's run flags  (usage, build family, since 1.15.0)

  A compiled program takes the run's flags first and its own arguments after them; this one is not a run flag, it lacks its value, or an argument is not valid UTF-8. Nothing ran.

  what to type next: put the program's own arguments after --: tool -- --flag (tool --help lists the run flags)

  known causes, ranked; doctor checks them in this order

     probe: none; a suggestion, not a finding
     remedy: move it after --
  2. a mistyped run flag (refused, so a mistyped --dry-run never becomes a real run)
     probe: none; a suggestion, not a finding
     remedy: spell it as tool --help shows it

======== E1053 ========
E1053 not this program's run  (usage, build family, since 1.15.0)

  kind of no: these are MY ciggies  (the door: it knows you and said no; 403 Forbidden; permission denied; a lock; a refusal by policy)

  A compiled program puts back only the runs it made (`--unburn`); the run named was made by a script or by another program.

  what to type next: use cig unburn <run> for any run, or the program that made it

  known causes, ranked; doctor checks them in this order
  1. the run id belongs to another script's or program's run
     probe: run-record (run.json for the run: status, pid, totals)
     remedy: cig runs <run> shows which script or program made it

  arises in: unburn

# Speed baseline, 2026-11-13: carton 0.1.0 before the bytecode VM

<!-- SPDX-License-Identifier: CC-BY-4.0 -->

The baseline cig-script#213 asks for, taken before the VM runs programs: every product's own suite, the floors and comparators with the same harness, start-up, peak memory, sizes and instruction counts. Nothing was tuned. Each repository's `bench/baseline-2026-11-13.json` holds the case-by-case numbers; this file holds #213's tables with "today" replaced by what was measured.

## Conditions

- **Machine:** a 2018 laptop, Intel Core i5-8265U (4 cores, 8 threads, 1.6 to 3.9 GHz), 7.4 GiB RAM, NVMe SSD, btrfs. One of #213's three machines; the desktop and CI baselines are still to come.
- **System:** Parrot Security 7.4 (echo), kernel 7.2.11+parrot7.1-amd64, CPU governor `powersave`, power profile `balanced`, on mains power (battery 77%).
- **Load:** one job at a time under the test machine's lock; nothing else ran during a timing job.
- **Page cache:** warm (each case has one untimed warm-up), except the rows marked cold, which drop the page cache before every sample.
- **Measured:** the released carton 0.1.0: cig 1.21.0, cig-orchestrator 1.19.0 (cig 1.21.0), cigcompile 0.4.0 (makes programs for cig 1.21.0), cigar 0.1.0, ciginstaller 0.1.0; each repository's manifest and fixtures from `main` (cig-script b936521, cig-orchestrator b15bbf8, cig-compile 7a3bb2d, cigar-script 3136868, cig-installer 9b11198).
- **Comparators:** Python 3.13.5, Node v20.19.2, go version go1.27.3 linux/amd64, GNU Make 4.4.1, bash 5.2.37, just 1.40.0, tsc 4.9.5, rustc 1.99.1 (58cf8f9c3 2026-10-13), rustup 1.29.3 (edbc831ce 2026-11-02). Not installed (not packaged for this system): `task`, `mise`.
- **Two rounds:** every timing job ran twice, as separate runs: round 1 from 08:33 to 09:16 UTC, round 2 from 08:58 to 09:11 UTC (job start times). Times are given as `round 1 / round 2`; `~` marks a median that moved more than 5% between them (noisy). The statistics are `cig bench`'s: median, p10 to p90 and CV over the samples; the JSON files carry all of them.
- **Peak memory** is the program's own: `ru_maxrss` from `wait4`, the command forked from a small C parent, five runs. `cig bench`'s own RSS column adds the harness's resident set to every child (`true` reads 9.1 MB there), so it is kept in the JSON but not used here.
- **Instruction counts:** `perf stat -e instructions:u` (user space, children included), median of five runs; they agree between the rounds to within 0.1%.

## `cig bench --family`

It runs on this layout only with every product named: `cig bench --family --product cig=<cig-script> --product cigo=<cig-orchestrator> ... --with cig@<released cig> --with cigo@<released cigo> ...`. All five suites ran in one report and every case was timed (cig 33, cigo 14, cigcompile 62, cigar 67, ciginstaller 3); the result is in cig-script's file under `family`. What the bare `cig bench --family` needs:

- **The suites in the installer's layout.** Finding a product through the installer needs `<prefix>/share/<name>/bench/bench.toml`; carton 0.1.0's toolchains hold `bin/` only (cigo's also its docs and `orchestrate.cig`), so nothing is found.
- **The released binaries, not the checkout's.** Without `--with`, a family run takes each product's `[bench].binary` from the checkout: an unbuilt `target/release/<tool>` for cig, cigcompile, cigar and ciginstaller, and main's `bin/cigo` (main's `orchestrate.cig`) for cigo.
- The family report gives cigo's `version` as `null`.

## Not measured, and why

- **cig, wait times at any history (#188):** no suite builds a home with a large run history.
- **CigarScript at scale against `tsc`, `mypy`, `pyright`:** no corpus of the same size and shape in those languages; the cigar side is measured.
- **CigarScript language server:** waits on cigar-script#16.
- **cigcompile typed programs against Rust:** no typed program builds before stage D (cig-compile#34).
- **cigcompile build time against `go build`:** no Go program of the same size; the cigcompile side is measured.
- **The installer: a shim in front of a real tool, a carton install, `check`, five cigo versions on disk, an update with nothing to do:** the installed shims stop at E1903 (below); an install needs a local mirror (`ciginstaller bench --from`); `check` needs a cached manifest; the disk ratio needs two or more cigo versions; an update needs the network.
- **`task` and `mise` as comparators:** not packaged for this system, so not installed.
- **The desktop and CI machines:** this file is the laptop's baseline only.

## What the baseline found

Reported, not fixed: each belongs to the issue named.

1. **cigo's per-call cost is checking orchestrate.cig.** `cig check orchestrate.cig` alone is 229M of `cigo --version`'s 342M instructions (67%) and 57.7 of its 59.7 MB. The verdict cache saves 57M instructions per hook call but not the check, so a cached hook is still 65.3 ms against a 5 ms target (cig-orchestrator#117, cig-compile#71).
2. **Compiled programs are slower than interpreted ones at stage A** on the compute programs (geometric mean 0.89x; nbody, mandel and fannkuch 1.35x to 1.47x slower), where stage A is meant to be at parity (cig-compile's docs/BENCHMARKS.md): both sides run the same runtime bytes. Not profiled here (cig-compile#31). The set as a whole is at 0.99x.
3. **`cigar run` is 2.3x slower than `cig run`** on the shared compute set (up to 5.1x on strbuild) and uses 33 MB against cig's 14.7 MB (cig bench's RSS column) (cigar-script#17).
4. **`cigar check` of exhaustive `match` grows faster than the code:** 114 / 114 ms at 1,000 lines, 3940 / 3958 ms and 309 MB at 10,000 (cigar-script#9, cigar-script#17).
5. **cig's start-up has two modes**, about 2.4 ms and about 7 ms for the same `hello`, with 2.1M user instructions either way; the peak is 14.9 MB against `python3`'s 9.7 MB, and its own work is small: 2.1M user-space instructions (a Go hello: 0.42M; `python3 -c pass`: 44M) and 212 page faults (Go: 105). At this clock 2.1M instructions take well under 1 ms, so most of the 2.4 to 7 ms is process set-up, faults and kernel time, not cig's code (transparent huge pages are `always` on this system). That is a count, not yet a profile; #213's arena note (mimalloc 3's 2 MiB pages) is the first suspect (cig-compile#30, cig-script#210). The compiled hello is the same shape: 0.96M instructions, 137 faults, 15.0 MB. The `burn one write` case's 7 ms budget is missed (7.81 / 7.88 ms).
6. **The burn is about 4x to 42x a plain write + fsync loop** over the same files (#147; the floor itself moved between rounds); unburning the 1,000-file tree takes 1.4x its burn.
7. **`cig bench <file>` with a bare file name fails every case** ("could not start: No such file or directory"): the manifest's folder is `Path::parent()` of the argument, which is empty for a bare name, and the empty path becomes the cases' working directory. `./<file>` works.
8. **`cigcompile bench --json` 0.4.0 reports the harness's resident set for every side** (23.6 MB for a 1 ms Rust program); the docs say 0.4.1 fixes it.
9. **The installed shims on the test machine stop at E1903** ("the build for `cig` ... is not the file its receipt recorded"): the toolchain files' device, inode or modification time changed after install, most likely when the machine's disk was restored from a snapshot. `ciginstaller repair` is the documented fix; the shim's own time comes from `ciginstaller bench` instead.
10. **`cigcompile` hello is 15.8 MB against Go's 2.3 MB**: the whole runtime is in the file (cig-compile#14's 4 MB waits on stage B).

## The files

Each `bench/baseline-2026-11-13.json` starts with `conditions` (the machine, every tool's version, the binaries' sizes, each job's start time, battery and load), then:

- `suites`: the product's own suite as `cig bench --json` gives it, one entry per case (`name`, `group`, `outcome` with `median_ms`, `p10_ms`, `p90_ms`, `cv`, `samples`, `rss_bytes`, `metrics`), with **three additions**: `outcome_round_2`, `spread_between_rounds` and `noisy_between_rounds`;
- `start_up`: the start-up rows and floors, in the same shape (`cig bench`, 15 samples of 20 back-to-back runs, fewer for the slow ones, 1 for the cold rows);
- `peak_rss`: the program's own peak, `ru_maxrss` from a small C parent, five runs (it departs from `cig bench`'s `rss_bytes`, which includes the harness's resident set);
- `instructions`: `perf stat -e instructions:u`, five runs, median, min, max and round 2's median;
- cig-script's adds `compute_against_references` (the 16 compute programs and the start-up programs, each as cig, CPython and Node) and `family`; cig-compile's adds `set_harness`, `cigcompile bench --ref --json`'s own shape (raw samples left out); cig-installer's adds `budgets`, `ciginstaller bench --json`'s own shape, both rounds.

The `rss_bytes` that `cig bench` records include its own resident set (about 9 MB on this machine); use `peak_rss` for memory.
